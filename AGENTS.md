# Architecture

- Keep the Expo mobile app in this repository; VPS platform changes are reviewed overlays under docs, not deployments, because platform writes require separate approval.
- Read authentication, database, and web origins separately; mobile uses only the VPS public key, because cloud sessions and VPS sessions are not interchangeable.
- Keep identity proof and account issuance in existing server-side login helpers; expose bounded JSON handlers instead of calling internal server-function URLs.
- Treat VPS overlays as deployment source rather than Expo modules; exclude them from mobile type resolution and exercise their browser-safe HTTP boundary with Jest's TypeScript transformer.
- Keep account-entry presentation in a shared native selector and derive selectable contexts from actual server memberships; choosing an entry is not a permission grant.
- Home sections per role live in `src/lib/sections.ts`, mirroring the platform's NAV_BY_ROLE and permission gating; keep it in sync with the platform instead of inventing role menus.
- Shared motion rules live in `src/lib/motion.ts` and `useReducedMotion`; every animation or press scale must go through them so the system "reduce motion" setting disables it.
- Sign-in starts on `WelcomeScreen` (role cards); choosing a role opens the tabbed sign-in form and back returns to welcome — keeps the approved login design flow in one place.
- Students get a five-tab shell (`StudentShell` in App.tsx, screens in src/screens/student/); every student section reads the same platform sources as the web pages (RPCs/tables in `src/api/student.ts` and `src/api/family.ts`), with display rules mirrored in `src/lib/studentData.ts`; never show placeholder data.
- Student tab screens use their own visual layer (`src/theme/student.ts` palette, `src/components/student/SKit.tsx` primitives, Readex Pro via `FontSetContext` around `StudentShell`), with time/due rules in `src/lib/studentDay.ts`; staff roles keep `tokens.ts` and Cairo; guardian reference screens explicitly opt into their own visual adapter.
- Guardian presentation uses `theme/guardian.ts`, `components/guardian/GKit.tsx`, and Readex via its shell; separate guardian attendance/homework views preserve shared student logic without restyling student or teacher screens.
- Guardians use a school-keyed five-tab shell in src/screens/guardian/GuardianScreens.tsx; children come from `family_children` (verified + can_follow only), and per-child screens reuse the student screens inside `StudentScope`, because the platform RPCs authorize both self and guardian (is_student_self / is_guardian_of).
- Sections shared by both roles (conversations, classrooms, pickup, events, notifications) live in src/screens/shared/; server permissions decide access, the app only mirrors the platform's role rules (e.g. comments for students only, consent for guardians only).
- Sections the platform hides (virtual classes) or whose access is not confirmed for a role (guardian grade results) stay out of the app until verified with a real account.
- Teachers use a five-tab shell in src/screens/teacher/ (TeacherShell + TeacherSections); every section calls the same platform RPCs as the web pages (la_*, adm_*, homework_list, edu_find, timetable_slots) via src/api/teacher.ts, with display rules in src/lib/teacherData.ts; authoring flows not yet ported stay out rather than being faked.
- Teacher homework/test authoring rules live in src/lib/homeworkRules.ts and src/lib/examRules.ts (pure, tested) and mirror the platform forms; the server RPCs stay the authority for permissions and state transitions.
